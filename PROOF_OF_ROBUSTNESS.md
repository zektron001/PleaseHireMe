## 2. Performance: every guarantee is affordable

Ten measurements, each run hundreds of times, each with a budget written down
before the number was taken. **Every p95 landed inside its budget.**

| Measurement | p50 | p95 | Budget | Headroom at p95 |
| --- | ---: | ---: | ---: | ---: |
| `live.fanout.50-watchers` | 0.006 ms | 0.013 ms | 2 ms | **154x** |
| `live.board.poll` | 0.654 ms | 1.542 ms | 40 ms | **26x** |
| `concord.doc.read` | 0.896 ms | 3.586 ms | 30 ms | **8.4x** |
| `concord.write.small` | 1.396 ms | 3.286 ms | 15 ms | **4.6x** |
| `concord.write.contended` | 1.248 ms | 1.796 ms | 250 ms | **139x** |
| `concord.provenance` | 46.951 ms | 81.131 ms | 300 ms | **3.7x** |
| `concord.section-check` | 49.261 ms | 99.843 ms | 300 ms | **3.0x** |
| `concord.merge3` | 92.668 ms | 130.872 ms | 300 ms | **2.3x** |
| `concord.write.large` | 71.618 ms | 125.869 ms | 400 ms | **3.2x** |
| `concord.write.large-allocated` | 110.747 ms | 142.743 ms | 500 ms | **3.5x** |

### Why these are the right numbers to care about

**Fan-out to fifty watchers costs 13 microseconds at p95.** This one matters
more than its size suggests, because the tap sits in `inspect`, which the runner
calls for every line Codex emits. A slow fan-out would not make the interface
laggy, it would slow the *Agent* down. At microseconds for fifty subscribers,
that risk does not exist, and the design keeps it that way: a subscriber that
throws is dropped rather than retried, and nothing in the path awaits anything.

**The board poll costs 1.5 ms at p95 against a two second poll interval.** That
is under a tenth of one percent of the interval. The board deliberately holds no
state of its own: it recomposes sessions, warrant roles, conflicts, presence and
usage on every request, so there is exactly one source of truth per fact. That
trade is only defensible if recomputation is cheap, and this number is what makes
it defensible. Caching here would buy nothing measurable and could serve a stale
conflict count, which is the one thing a merge gate must never do.

**Contended writes cost 1.8 ms at p95 against a 250 ms budget.** This is the
number that says concurrency is genuinely solved rather than merely survived.
Several Agents racing on the same document serialise through a per document lock,
and the queue does not become the bottleneck. See `apps/server/src/concord/`.

**The expensive operations are the honest ones.** Three way merge, provenance
recomputation and the section ownership check all sit in the 46 to 131 ms range.
They are the most algorithmically real work in the system, they happen once per
Agent turn rather than once per request, and an Agent turn takes 20 to 120
seconds of model time. A hundred milliseconds inside a ninety second turn is
noise. They still finish in a third of their budgets.

**Large writes stay bounded.** A large document write is 126 ms at p95, and the
same write with section allocations enforced is 143 ms. Adding ownership
enforcement to a write costs roughly 17 ms, which is what it costs to buy the
guarantee that no Agent can touch another Agent's section.

## 3. Robustness: what it survives

### Property based fuzzing at 20,000 cases

The merge, provenance and warrant resource algorithms are not tested with a
handful of examples. They are fuzzed with `fast-check` at **20,000 generated
cases per property** (`FUZZ_RUNS=20000`, see `apps/server/package.json`), on top
of a 200 case pinned lane that runs on every commit.

This is the part of the suite we are proudest of, because it found things no
human would have written a test for. A three way merge that reduces a document
to a single blank line used to lose that line, and the same collapse lost the
line's provenance with it. Both are now pinned, named, and pointed at the exact
source line (`merge.ts:131`, `provenance.ts:100-102`).

### Zero regressions across 158 suites

The baseline lane exists to answer one question, and it answers it cleanly:
**465 of 465 passing, no regressions, no suite that silently failed to load.**
That last clause is not filler. The suite has a test whose only job is to report
test files that never loaded, because a suite that vanishes looks exactly like a
suite that passes.

### The system refuses what it says it refuses, live

Verified by hand against a running instance, not only in a harness:

- Signed in as the orchestrator, pressing Run on an Agent that acts for Bob is
  refused by the server with **`Only human:bob may run this Agent`**. Screenshot
  in `docs/assets/mw-refusal.jpg`. The user id is never read from the request, so
  there is nothing in the browser to tamper with.
- The merge gate stays shut with **"2 still to approve"** until every Agent is
  approved by its own human. Screenshot in `docs/assets/mw-merge-gate.jpg`.
- Every decision, allow and deny alike, lands in a hash linked chain
  (`prevHash` to `hash`, `apps/server/src/aegis/audit.ts`). Screenshot in
  `docs/assets/mw-decision-chain.jpg`.
- `npm run demo:warrant` walks the whole delegation story in about two seconds
  with no API key, ending in the required cross owner denial.

### It runs where we say it runs

- **A full Agent turn completes inside the Docker container**: one turn, roughly
  two minutes, ending in a real `CONCORD-COMMIT` and 168,206 input tokens of
  actual model work.
- **A fresh clone with no `.env` reaches a running app in one command.**
  `./try.sh` was tested by cloning into an empty directory: it generated a
  token, built the image, started it, waited for health and printed the URL,
  exiting 0.
- **20 out of 20 automated interface checks pass against the built container
  image**, not just against the dev server.

## 4. Why 29 audit findings is a strength, not a weakness

The audit lane does not ask "does the code work". It asks a harder and more
useful question: **what does this system do that its own documentation denies?**
Then it writes a failing test for every gap it finds, names the file and line,
and leaves it failing on purpose until someone fixes it.

That is why the number is not zero, and why we are showing it to you rather than
quietly deleting it. A suite that only contains tests the code already passes
tells you nothing about the code. Roughly two thirds of these findings are
labelled `REAL FINDING, pinned` in the source, which means a human read the
behaviour, decided it was wrong, and chose to record it rather than hide it.

Concrete evidence that this mechanism works: two of the worst bugs in this
project were described by a failing test *before* a human hit them.
`broker-target.contract.test.ts` predicted that every local Agent turn would
hang for ten minutes against an unreachable host, in writing, with the reasoning
spelled out. When we hit exactly that hang, the diagnosis was already sitting in
the repository. **That test now passes**, because the bug it described has been
fixed (`apps/server/src/index.ts` now decides the upstream from where Codex
actually runs).

The findings that remain are documented, categorised and open. They are listed
in full in `artifacts/tests/REPORT.md`, and the limitations they imply are
written up honestly in `docs/THREAT_MODEL.md` and
`docs/WARRANT_TRACK_B.md` section 8.

## 5. What these numbers do not claim

Being straight about this is part of the point.

- The audit and fuzz lanes are **not** green, and we are not presenting them as
  green. 29 findings are open.
- The performance numbers are single machine measurements of the middleware
  itself. They do not include model latency, which dominates any real turn.
- AEGIS containment (sandboxing, our unclaimed track) derives file and network
  intent by scanning shell text, which cannot be parsed reliably. It is
  documented as an open structural issue in `HANDOFF.md` section 5a, and the
  try it build ships with it off so that a first time visitor can complete a run.

None of that undercuts the two claims this document does make: **the system does
not regress, and every guarantee it offers is cheap enough to keep.**

## 6. Reproduce all of it

```bash
npm run check        # typecheck, then every test, then a real build
npm run test:report  # regenerates artifacts/tests/REPORT.md and the JSON behind it
npm run test:fuzz    # the 20,000 case campaign on its own
npm run test:perf    # the performance lane on its own
npm run demo:warrant # the delegation story end to end, about two seconds
```

Raw evidence lives in `artifacts/tests/`: `baseline.json`, `audit-server.json`,
`audit-web.json`, `fuzz.json`, `perf.json` and `perf-measurements.json`, plus the
generated `REPORT.md`. Nothing in this document was typed by hand from memory.
